# TASK-18: Smart Office Demo UI — Notification Dispatch (Capability 3 presentation layer)

## Correction history
**Revision 1 (2026-09-25)** — initial proposal, produced by independent repository discovery (source code + tests + git history, not planning documentation alone) plus a human-review gate on the two backend additions this task requires. Both were approved on 2026-09-25 (see "Risks and human decisions").

**Revision 2 (2026-09-25, implementation clarifications, pre-implementation)** — two gaps identified before implementation begins, corrected here without changing scope, architecture, or the two already-approved backend additions:
1. **Notification polling must resume when the associated booking transitions to `Released`, even if the `Confirmation` notification already reached `Sent`.** As originally scoped, the notification panel's polling settled permanently once every *currently known* row was terminal — but `Confirmation` typically settles (`Sent`) within one worker tick, long before release, while the `ReleaseNotice` row does not exist yet at that point. A panel that had already settled would never observe the later-created `ReleaseNotice` row. Fixed in Scope §E below by making the polling hook resume on a `Released` transition, not just on mount/timeout.
2. **Scenario C (provider-failure recovery) is made deterministic**, and terminal `Failed` is split out into its own separate demonstration rather than an alternate ending the presenter might stumble into by waiting too long: the provider must be restored while `attempts < DEFAULT_MAX_ATTEMPTS`; the procedure explicitly respects the real worker-tick/backoff schedule instead of an arbitrary wait; the notification panel gains a bounded timeout plus a manual refresh control so a process-restart procedure that outlives the panel's own poll window can still be observed without a page reload; and terminal `Failed` is now Scope §D, its own scenario, proving restoring the provider does **not** retroactively recover an already-terminal row.

No change to the two human-approved backend items, the API contracts, the out-of-scope boundary, or any backend reliability guarantee (TASK-11/12's code, schema, retry policy, and crash-window behaviour are untouched) — both corrections are frontend polling-hook behaviour and demo-procedure precision only.

## Purpose
Extend the existing Smart Office React application ([TASK-17](TASK-17-capability2-demo-ui.md)) so all three approved PoC capabilities — Booking Creation, Automatic Release, and **Notification Dispatch via Transactional Outbox** — can be demonstrated from one coherent browser session. This is a human-approved presentation-layer addition, not a fourth PoC capability: it introduces no new business event, no new notification type, no change to the outbox schema, the claim/lease worker, the retry/backoff policy, or the at-least-once guarantee. Every notification status shown in the browser is read verbatim from the real `notification` table via a new minimal, read-only, booking-scoped endpoint — never computed, inferred, or simulated in React.

## Human-approved backend enablement (dependency work bundled into this task)
Approved by human review on 2026-09-25, in response to the two gaps above. Each item is minimal, reuses existing tested logic, and carries no independent business value beyond letting the UI observe real backend state:

1. **`GET /bookings/:id/notifications`** — new read-only route in [booking.routes.ts](../../src/modules/booking/booking.routes.ts), registered inside the same authenticated child context as `GET /bookings/:id`.
   - A new service function (e.g. `getNotificationsForBooking(bookingId, employeeId)` in `booking.service.ts`, or `notification.service.ts` depending on final module placement — implementer's call, not an architectural decision) first resolves booking ownership using the **same check `getBookingForEmployee` already uses** (`BookingNotFoundError` if the booking does not exist or does not belong to the requesting identity — no cross-employee enumeration, identical boundary to `GET /bookings/:id`), then queries the `notification` table scoped by `booking_id` only.
   - A new repository function (e.g. `findNotificationsByBookingId`) in `notification.repository.ts` reuses the existing `NotificationStatus` type and row-mapping convention already established by `claimNext`/`markSent`/`recordFailure`.
   - `200` → `{ notifications: [{ id, type, channel, status, attempts, sentAt }] }`. Deliberately excludes `lease_owner`, `lease_expires_at`, and `dedup_key` — internal worker mechanics, not demo-relevant, and excluded per the "no sensitive diagnostics" boundary.
   - `404` if the booking does not exist or does not belong to the requesting identity — identical shape/behaviour to `GET /bookings/:id`.
   - `401` on missing/invalid bearer token, identical to every existing route.
   - **Known limitation, not fixed by this task**: the `notification` table has no creation-timestamp column (only `sent_at`, populated on success). Response ordering is not guaranteed to be chronological by a timestamp; since a booking has at most two rows (`Confirmation`, `ReleaseNotice`) and `type` alone disambiguates them, the frontend renders by known type, not by array order. Adding a `created_at` column is a schema change with no scenario in this task that requires it — out of scope.
   - This is deliberately narrower than a general notification-management API: single-booking scope, read-only, no list-all, no cross-employee access, no provider secrets.
2. **`NOTIFICATION_DEMO_FORCE_FAIL` environment variable**, read once in `startApp()` ([server.ts](../../src/api/server.ts)) at process start, wired into the `FakeNotificationChannel` constructor already built there:
   ```ts
   const forceFail = process.env.NOTIFICATION_DEMO_FORCE_FAIL === "true";
   const notificationChannel = new FakeNotificationChannel(
     forceFail ? { shouldFail: () => true } : {},
   );
   ```
   - **No new HTTP endpoint, no runtime toggle.** Flipping provider availability requires restarting the local process with (or without) the variable set — an explicit, human-approved trade-off (see "Risks and human decisions"): safer (zero new mutable control surface, no new attack surface) at the cost of a live demo requiring a process restart rather than a button click.
   - Same trust model as every other local `.env`-style config already in this PoC (`DATABASE_URL`, `PORT`, `NOTIFICATION_WORKER_INTERVAL_MS`) — local-only, never a cloud or shared-environment concern (per plan §1 decisions 3/8).
   - `StartAppOptions` (already an injectable options object — `clock`, `port`, `sweepIntervalMs`, `notificationWorkerIntervalMs`) gains one more optional field (e.g. `forceNotificationFailure?: boolean`) so integration tests can exercise this deterministically without mutating `process.env`, consistent with the existing dependency-injection pattern in `server.ts`.
   - Documented in `.env.example` as a commented-out, demo-only line, consistent with how `DATABASE_URL` is documented there today.

Neither item is exposed as an unrestricted production endpoint beyond what already exists in this local-only, no-cloud PoC (per plan §1 decisions 3/8) — same trust model as every other route/config in this app today.

## Scope

**A. Booking Confirmation Notification Visibility (Scenario A)**
After a booking is created (existing `SearchPanel` or `DemoScenarios` Scenario 1 flow, unchanged), the booking card additionally fetches/polls `GET /bookings/:id/notifications` and renders the `Confirmation` row's `status`, `attempts`, and `sentAt` — sourced entirely from that response. The card must never display or imply a notification was sent merely because `POST /bookings` returned `201`; the notification section renders `Pending`/`Sending` distinctly from `Sent` until the backend actually reports `Sent`.

**B. Automatic Release Notification Visibility (Scenario B)**
Reuses `DemoScenarios` Scenario 2 (automatic release, unchanged — same employee, same-day Belgrade Desk, no check-in). Once the existing polling ([useBookingPolling](../../frontend/src/useBookingPolling.ts)) observes `Released` (real Release Engine sweep, unchanged), the same notification panel from §A now also shows the `ReleaseNotice` row transitioning `Pending → Sent`, and confirms the released resource reappears in availability (existing, unchanged `GET /availability` re-search).

**C. Notification Provider Failure — Deterministic Recovery (Scenario C)**
Because the failure control is a boot-time env var (per the approved decision, no live HTTP toggle), this is a short, deliberately **deterministic operator procedure** — the provider is restored well within the retry policy's cap, so the outcome is recovery, not a race against the backoff schedule:
1. Presenter restarts the local API process with `NOTIFICATION_DEMO_FORCE_FAIL=true npm run start:api`.
2. Presenter creates a booking (Scenario A or B flow) in the browser. `POST /bookings` still returns `201` — booking success is unaffected.
3. The notification panel shows the `Confirmation` row at `Pending`/`Sending`, `attempts` incrementing on each worker tick per the real retry/backoff schedule — `NOTIFICATION_WORKER_INTERVAL_MS` (default 5000ms worker tick) and `attempts × 2000ms` backoff gate per attempt, capped at `DEFAULT_MAX_ATTEMPTS` = 5 ([notification.service.ts:13-15](../../src/modules/notification/notification.service.ts:13)) — never reaching `Sent` while the flag is set.
4. **Presenter restores the provider after observing 1–2 failed attempts and explicitly before `attempts` reaches `DEFAULT_MAX_ATTEMPTS`** — restart the process without the env var. This is the deterministic constraint that makes this "the recovery scenario": the manual checklist (Verification evidence) records the observed `attempts` value at restart to confirm the row was still `Pending`/`Sending`, never `Failed`, at that moment.
5. The newly-booted worker reclaims the still-`Pending` row on its next tick, respecting the row's own backoff gate (no immediate reclaim before the gate elapses), and it transitions to `Sent` — the real retry/backoff mechanism, not simulated or shortcut.
6. If the notification panel's own bounded poll (§E) has already timed out by the time the presenter finishes the restart, the presenter uses the panel's manual "Refresh notifications" control (§E) to observe the `Sent` transition without reloading the page or losing the session's tracked bookings.
7. At every point, the UI keeps booking success (step 2) and notification delivery status (steps 3–6) visually and textually separate — no combined "booking + notification" success indicator.

**D. Notification Provider Failure — Terminal State (separate demonstration)**
A distinct, separately-triggered demonstration that the retry policy has a real terminal state — this is **not** a branch of Scenario C that the presenter falls into by waiting too long, and restoring the provider does **not** automatically recover it:
1. Presenter restarts with `NOTIFICATION_DEMO_FORCE_FAIL=true` and creates a **new** booking (not the one used in Scenario C), as in Scenario C steps 1–2.
2. Presenter deliberately leaves the provider failing — no restart — until the notification panel (or a manual refresh, §E) shows `attempts` has reached `DEFAULT_MAX_ATTEMPTS` and `status` is `Failed`.
3. Presenter then restores the provider (restart without the env var) and, via the panel's manual refresh, confirms the row **remains `Failed`** — the backend's claim query only ever matches `Pending`/`Sending` rows ([notification.repository.ts:88-101](../../src/modules/notification/notification.repository.ts:88)), so a `Failed` row is never reclaimed regardless of provider availability. This is the retry policy's own documented boundary, not a defect.
4. Run as its own pass, on its own booking, never interleaved with Scenario C's recovery pass — so Scenario C's deterministic outcome is never put at risk by this one, and this one's terminal outcome is never mistaken for a stuck recovery.

**E. Notification Status Panel**
A new, small React component (e.g. `NotificationPanel.tsx`), rendered inside the existing booking card, receiving the tracked booking (including its live `status`, as already tracked by [useBookingPolling.ts](../../frontend/src/useBookingPolling.ts)) and its owner token. Fetches `GET /bookings/:id/notifications` on mount and on a bounded poll, via a new `useNotificationPolling.ts` hook mirroring `useBookingPolling`'s interval/timeout/backoff-on-error conventions, with three properties required by this task:
- **Settle condition**: polling stops once every currently-known row is `Sent` or `Failed`.
- **Resume on booking-status change**: the hook takes the tracked booking's live `status` as an input dependency. Whenever that status transitions to `Released`, the hook resets its own settle state and resumes polling for this booking's notifications — even if it had already settled because the `Confirmation` row reached `Sent` well before release (the common case). This closes the gap where a new `ReleaseNotice` row, created only at release time, would otherwise never be observed by a panel that had already stopped polling. Rows are matched by `type`, not array position, consistent with the "no ordering guarantee" limitation already noted under "Human-approved backend enablement" item 1.
- **Bounded timeout + manual refresh**: like `useBookingPolling`, the hook has its own timeout (e.g. default 30s) after which `pollState` becomes `"timeout"` rather than polling forever. The hook additionally returns a `refresh()` function; `NotificationPanel` renders a "Refresh notifications" control, available once `pollState` is `"timeout"`, that calls `refresh()` to force one fetch and re-evaluate settle state — needed because Scenario C/D's process-restart procedure can outlast the panel's own bounded poll window, and a full page reload would lose `App.tsx`'s in-memory tracked-booking session state.

Renders one row per notification: Type | Status | Attempts | Sent At, using the same pending/success/error visual conventions `BookingCard` already uses for check-in/release states.

**F. Timeline Correction**
[Timeline.tsx:13-14](../../frontend/src/Timeline.tsx:13)'s disclaimer is corrected to remove the now-false "Capability 3 is not implemented in this PoC" claim, replaced with accurate language (e.g. "notification status is observed via `GET /bookings/:id/notifications`, never implied by booking success"). One new `TimelineEventKind` (e.g. `"notification_status_observed"`) is added to `types.ts` and fired when the notification panel observes a terminal (`Sent` or `Failed`) status — mirroring how `checkin_confirmed`/`release_confirmed` are already fired from real poll observations.

12. No booking/release/notification business rule is duplicated or recomputed in React — every status shown is copied verbatim from a backend response field, and no new backend logic beyond the two minimal, human-approved additions above is introduced.
13. The only new backend controls are (a) a booking-scoped, read-only, authenticated GET endpoint returning no cross-employee data or provider internals, and (b) a local process-start-only env var with no HTTP exposure — neither is an unrestricted diagnostic or production control.
14. All three approved PoC capabilities (Booking Creation, Automatic Release, Notification Dispatch) are demonstrable end-to-end from the one existing React application in a single browser session, without a second frontend or a reload between capabilities.
